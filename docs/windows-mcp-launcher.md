# Windows MCPランチャー

Windows PowerShell 5.1／Windows Formsで受信サービス8791 → OAuth入口8792 → Secure MCP Tunnelを起動する。受信後は未保存プレビューで人が確認し、手動保存する。既存メモの読み出し・更新・削除は追加しない。

## 初回設定

1. このcheckoutで依存を`npm ci`により導入しておく。Node 22以上、Windows PowerShell 5.1が必要。システムCA／TLS検証を維持する。固定Tunnel buildは`0.0.16+5f99daabd4aa4a77049e6d81d54a0d8c18335397`。
2. `start-memo-nexus.cmd`をダブルクリックする。デスクトップにこのファイルへのショートカットを作れば、次回からコマンド入力は不要。ショートカットの引数に秘密情報を入れない。
3. 「設定」で既存のリポジトリ外OAuth設定JSONとtunnel-client.exeを選ぶ。OAuth設定は[認証付き受信の手順](mcp-http-oauth-receiver.md)どおりに用意する。ランチャーは8792の明示設定を要求し、resource・audience・issuer・利用者をTunnel IDから生成しない。
4. **既存**Tunnel IDとruntime keyを入力する。Auth0／ChatGPTの登録は作成・変更しない。keyは常に非表示。保持を選ばない場合、ランチャー終了までメモリ内だけに置き、次回は再入力する。
5. 使用中のMemo-Nexus URLを全文入力する。許可Originは既存と同じ`http://127.0.0.1:5500`または`https://tetsujisugimori-coder.github.io`。通常は従来の`/`、`/index.html`、`/memo/`、`/memo/index.html`を使う。localhost、別ポート、別プロファイルへ勝手に変更しない。URLにtoken、資格情報、query、fragmentを含めない。
6. 診断は通常OFF。「検証して保存」を押し、主画面の結果を確認する。設定検証では子プロセスを起動してNode依存、OAuth設定、固定buildと必要オプションを確認する。検証失敗なら入力内容を確認して再保存する。

画面はバックグラウンドrunspaceの検証中も応答する。起動・停止操作は重複実行しない。同じWindowsセッションでランチャーを二重起動すると既存画面の確認を案内する。

## 秘密情報の保存

通常設定は`%LOCALAPPDATA%\Memo-Nexus\launcher\settings.json`。設定パス、実行ファイルパス、Tunnel ID、明示URL、診断フラグ、暗号化keyのファイル名だけを保存する。

key保持を選ぶとWindows DPAPIの`CurrentUser`により暗号化し、同じフォルダーの`key-<ランダムID>.dpapi`へ別途保存する。フォルダーのDACLは現在ユーザーだけにする。独自暗号や平文key設定は使わない。同じユーザー・WindowsのDPAPIプロファイルが必要で、別ユーザー／別PCへのコピーは復号できる保証がない。

設定更新は新しい暗号化ファイルを書いた後にsettings.jsonを置き換える。直前の通常設定はsettings.previous.jsonに残る。以前の暗号化ファイルは自動削除しない。保持をOFFにして保存した場合、現在の設定は暗号化ファイルを参照しなくなるが、過去の暗号化ファイルは残る。削除が必要なら停止後にこのlauncherフォルダーだけを明示的に管理する。受信履歴フォルダーを削除しない。

復号不能・設定不正の場合は起動を拒否する。「設定」でkeyを再入力し、保持の有無を選んで再保存する。自動初期化・接続先変更・認証なしへの切替は行わない。

Browser token／Adapter tokenは受信サービスを新規起動するたびに独立した256-bit乱数として生成する。同じAdapter tokenを8792の子環境へ直接渡すので、通常の手動コピーは不要。Browser tokenは「Browser tokenをローカルで確認」から必要時だけ確認・手動コピーし、**既存の受信画面**に入力する。自動ブラウザ注入は行わない。チャットやログへ貼り付けず、使用後はクリップボードを消す。

各子の環境変数は役割別に作り直す。受信子には2 tokenと既存履歴の基準となるLOCALAPPDATA、OAuth子にはAdapter token、システムCAと明示診断フラグ、Tunnel子にはruntime keyとTunnel IDだけをOS実行用変数に追加する。NODE_OPTIONS、proxy資格情報、他のAI key、任意のTunnel設定は引き継がない。秘密値をargv、URL、平文設定、画面の診断、ログへ出さない。子のraw出力は転記せず、固定日本語診断だけを表示する。Tunnelのraw HTTPログは常にOFF。

## 通常の操作

- 「MCPを起動」：Node依存・設定・build・8791／8792競合・既存Tunnelを検査し、受信 → OAuth → Tunnelの順で起動する。固定時間経過だけで成功にしない。
- 8791：既存の永続履歴を開いた受信サービスへ、現在のBrowser tokenを用いてpendingを読み、準備を確認する。読み取った未保存内容は診断へ表示しない。
- 8792：既存と同じmetadataのresource／authorization_servers／scopes_supported完全一致、Bearerなし401とresource_metadata案内を確認する。この401は正常な起動プローブで、認証失敗の表示に使わない。
- Tunnel：既存と同じID別mutex・固定build・起動引数を使う。loopbackの一時healthポートを明示指定し、待受が自分の子PIDに属することと`/readyz` 200を期限内に確認する。healthポートの競合や所有者不一致は成功にしない。
- 「Memo-Nexusを開く」：明示設定URLを既定ブラウザで開く。ローカルURLでは配信応答200も先に確認する。配信サーバーが不足していれば従来の静的配信を利用者が用意する。無関係な開発サーバーは起動しない。既定ブラウザが従来と異なる場合は、従来のプロファイルで明示URLを開く。
- 「停止」：今回のTunnel → OAuth → 受信の逆順に停止する。Node子にはstdinで終了を要求し、サーバーと履歴ロックを閉じる。期限内に終了しない場合だけ保持したProcessオブジェクトで終了する。Tunnelは保持したProcessオブジェクトで停止する。
- 画面を閉じる：停止ボタンと同じ処理を行い、停止を確認してから画面を閉じる。停止失敗時は画面終了を保留し、再度「停止」を案内する。

状態は「停止中」「起動中」「ローカル準備完了」「要対応」「停止処理中」。ローカル準備完了は今回の起動プローブの結果で、**ChatGPTとの接続成功・ツール検出成功・保存成功ではない**。子の異常終了を検出すると今回の残りの子も停止し、要対応を表示する。無制限の自動再起動はしない。

## 診断ON／OFF

停止後に「設定」で診断を選び、検証・保存して次回起動に反映する。OFFなら認証・initialize・tools/listは未観測。ONでは既存の安全な`memo_http_oauth` JSONイベントのうち、認証受理／拒否、initialize成功応答生成、実tools/list成功・toolCount=2・expectedTools=trueだけを固定日本語へ変換する。日時はランチャーが今回受け取った時刻。直近観測は停止／再起動でクリアし、ディスクに保存しない。

tools_prepared、単なるHTTP 200、過去の起動観測をツール検出成功にしない。応答生成を観測しても、Tunnel配送やChatGPTでの表示は利用者が別に確認する。転送ヘッダー拒否等の詳細調査には[既存の診断手順](mcp-http-oauth-receiver.md)を使う。

## 失敗時と復旧

既存の手動起動8791／8792／Tunnelがあれば競合を案内する。調査や試験のために無断停止・再起動・引継ぎをしない。利用者が元の起動端末と未処理プレビューを確認し、切替時に自分で停止してからランチャーを使う。今回の実装検証でも実プロセスは停止しない。

起動途中の失敗では今回の子だけを逆順に片付ける。PIDファイルは使わず、起動直後から保持したプロセスハンドルを使う。ポート／プロセス名だけで終了対象を決めない。以前のPIDによる停止や他プロセスの自動取込みは行わない。

受信履歴は従来どおり`%LOCALAPPDATA%\Memo-Nexus\received-history`を使い、画面にもこの保存先を表示する。親にMEMO_PREVIEW_HISTORY_DIRが指定されていれば起動を拒否し、既定履歴への暗黙の切替を防ぐ。独自の履歴ディレクトリで運用していた場合は、この初回版へ切り替えず従来起動を継続する。履歴のロック・破損・容量・権限問題は要対応として停止し、履歴削除・リセットを回避策にしない。履歴形式・保存基盤・ブラウザ領域は変更しない。

原文は永続履歴に保存されない。停止／再起動で未保存本文が失われる場合がある。同じ経路・同じOAuth利用者・同じrequestId・同じ原文で再送し、[既存の復旧手順](received-preview-recovery.md)で確認する。受信だけでは保存されず、保存済みか不明なら人がブラウザ保存領域を照合する。

ランチャーの強制終了・OS障害ではTunnelが残る可能性がある。Node子は親pipeのEOFで停止するが、強制終了直後の履歴ロック解放やTunnel停止を保証しない。次回は既存プロセス／ポートの競合として拒否し、引き継がない。起動元・プロセスの実体・作成日時を利用者が確認して対処する。履歴やブラウザデータは消さない。

## 検証と実機受入

`node memo-nexus-launcher.windows-check.js`は実PS 5.1と実受信履歴コードを使い、コピーした管理コードのポートを動的ポートへ限定する。OAuthとTunnelは明示的な模擬実装。実Tunnelプロセスガードを回避する変更は隔離コピー内だけで、製品コードには入れない。空白・日本語・アポストロフィのパス、DPAPI、準備・失敗・timeout・異常終了・逆順停止・子環境を検証する。実Auth0／ChatGPT／Tunnel成功の証拠にはしない。

現行の隔離fixtureは既存Node実行ファイルとJavaScriptだけを使い、試験用exeを生成・コピー・実行しない。version/helpの試験入力とTunnel役のhealth待受を試験コピーのプロセス生成関数で置換する。製品の固定build検査・役割別環境・TCP所有者照合・タイムアウト・終了条件は変更しない。別のfixtureプロセスがhealthポートを所有する場合は200応答があっても拒否し、そのプロセスを停止しないことを検査する。

GUIの自動試験は実Formsのイベントループで設定ダイアログ、未設定起動の拒否、停止、画面終了を検証する。試験コピー内のPerformClickとTimerを使うイベント試験で、実デスクトップでの人のマウス操作・表示・正常接続の受入とは分ける。実デスクトップの操作ツールから今回のForms画面を取得できず、画面を見た操作検証は未確認。起動した検証用GUIだけを作成日時と専用スクリプトで識別して片付け、ユーザーの既存サービスは停止していない。
