# Workerのライフサイクル

PoCの状態は「枠確保→Worker生成→readonly開始→結果待ち→結果照合→停止」。取消・世代変更時は先に受理権限を無効化し、`terminate()`を呼ぶ。停止前に生成済みまたは受信済みのmessageも、現在のsession、workerId、generation、requestIdが一致しなければ採用しない。同じ作業IDの重複処理・配送を防ぐ本番の管理は未実装である。

未解決Promiseは解決させずWorkerを停止できた。停止はPromiseを解決・拒否したことを意味しない。`terminate()`は戻り値も完了通知も持たず、CPU実行の停止、トランザクション終了、接続の解放、メッセージ破棄、GC／OS資源返却は別の事象である。PoCでは停止後の新Worker読取とDB version upgradeを観測したが、内部の解放時刻や常に即時に解放される保証は得ていない。

終了呼出しが例外を出す状況はPoC上で注入し、配送を停止し管理枠を保持して同じセッションの再生成を拒否した。実ブラウザが終了不能となる状況は再現できず、例外がなくても内部資源の解放を確認できない場合の安全な回復手順は未確立でHOLD。画面終了時も、全配送権限を無効化して所有Workerを停止する設計が必要だが、実OSの終了・凍結挙動は未検証。
