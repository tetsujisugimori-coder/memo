# 資源境界と方式比較

| 項目 | A：1セッション1Worker | B：画面固定数 | C：要求単位 |
|---|---|---|---|
| 分離 | セッション単位。停止不能ならその枠が残る | 枠共有。識別・予約が必要 | 要求ごとに分離しやすい |
| 未解決からの復旧 | 停止後に再生成 | 停止済み枠を再利用。終了未確認はHOLD | 停止後に別要求で再生成 |
| 上限 | セッション数とWorker数の両方に上限が必要 | 固定枠で明示できる | 同時実行数に上限が必要 |
| 生成・DB接続コスト | 初回中心 | 再利用で減る可能性 | 要求ごとに発生。性能未測定 |
| 連続検索 | 再利用しやすい | 待ち行列と公平性が必要 | 単発では隔離容易、連続性能未測定 |
| 取消・画面終了 | セッションのWorkerを終了、画面終了時に全停止 | 該当枠を停止、画面終了時に全停止 | 該当要求を停止、画面終了時に全停止 |
| モバイル | 接続とメモリがセッション数に比例 | 少数枠に抑えられるが他セッションへの容量影響あり | 起動頻度とバックグラウンド停止の影響が未検証 |

容量と利用可能性の両立には、最大枠、セッション単位の優先・公平性、期限付き待機または安全な拒否、旧作業の終了確認不能時のHOLDが必要。無制限の同時要求を必ず実行する保証はしない。終了未確認の枠を即座に実資源解放済みとみなさず、容量枯渇時に他セッションの要求を誤配送せず拒否する。Workerを多数作る方式は設計上の上限がなければ不可。

PoCは管理上の同時枠2件、12回の停止・再生成とDB upgradeを観測した。終了API呼出し回数と管理Mapの件数は実スレッドやメモリ使用量ではない。Worker内部の未解決Promise・DB接続・処理の実数をブラウザ外部から直接数えられていない。1回のWorker生成から初回結果までの実測はJSON参照。母数1の局所値で、DB接続単独の費用、連続検索の性能、iPhoneの制約を推定できない。
